# Постоянный протокол разработки и проверки сайтов

Версия: 2026-10-25. Применяется **по умолчанию ко всем будущим сайтам, интернет-магазинам, портфолио и демопрототипам**, а не только к Secret Maison. Если пользователь специально требует иной подход — это отдельное осознанное исключение.

## 1. Значки и Unicode — без emoji-сюрпризов

- Запрещено использовать текстовые символы со склонностью к emoji-рендерингу как элементы интерфейса: ↗, ↖, ➜, ➡, 🔗, 🔍 и подобные; не помещать их в текст кнопок/ссылок.
- Стрелки, поиск, корзину, внешние ссылки и прочие иконки создавать **inline SVG** или CSS-геометрией; `stroke: currentColor` / `fill: currentColor`; заданная толщина и размер. Не полагаться на emoji, вариационные селекторы или шрифт ОС.
- Использовать доступные подписи для иконок и кнопок; декоративные SVG скрывать от скринридера (`aria-hidden="true"`), у icon-only button должен быть `aria-label`.
- Для Safari/iOS явно задавать `color`, состояния кнопок, `appearance` при необходимости. Контроль системного синего цвета ссылок; если ссылка должна быть акцентной, задавать этот цвет осознанно через переменную темы.

## 2. Изображения товаров — подлинные, локальные, полные

- Не подменять товар фотографией похожей модели, другой комплектации, цвета или случайной интерьерной стоковой фотографией. Перед показом сопоставить точный артикул, модель и вариант с фотографией.
- Первое фото карточки показывает **весь товар**, не случайно обрезанную деталь; детали/ракурсы — следующие кадры. Для простых предметов достаточно 2–3 информативных фото, не множить однотипные крупные планы.
- Никаких фиктивных изображений или заглушек «вместо товара». Если общий вид не найден — сначала повторно искать его в фотобанке, затем отправить на ручной выбор; не выдавать карточку за готовую.
- Не делать внешние hotlink-URL основным источником товарных картинок на публикуемом сайте: такие URL могут поменяться, отдавать 403, блокировать стороннюю страницу или зависеть от чужого CDN. Импортировать **проверенные оригиналы в проект**, генерировать локальные оптимизированные WebP с понятной связью со SKU. Сохранять исходные URL в служебных данных.
- Перед публикацией программно проверить 200-код, декодирование, фактическую ширину/высоту, отсутствие битых/нулевых/дублирующихся фото. Проверить, что пути к ресурсам работают именно с учётом base path GitHub Pages.
- Все иллюстрации категорий и коллекций должны соответствовать своему смыслу и ассортименту; интерьерные атмосферные изображения отдельно маркировать как mood photography и не выдавать за фото конкретного SKU.

## 3. Данные каталога — без выдумок

- Реальные SKU, модель, характеристики, цены, размеры, коллекция и варианты проверяются по надёжному источнику. Не придумывать характеристики и цены для заполнения макета; явно отмечать непроверенные демонстрационные значения.
- Нормализовать размеры/материалы, разделять модель и исполнение, не смешивать чужие артикулы и фотографии. Категории/коллекции — независимые признаки, а не дубликаты товарных карточек.
- Импорты проводить без потери ранее корректных товаров и медиа. Перед заменой актуальных файлов — верификация и резервная копия. Не удалять действующие файлы сайта ради «очистки», если актуальность не подтверждена.
- Проверить согласованность индексной базы, карточек, фильтров и корзины, количество/уникальность ID, фото первых кадров, сохранность существующих данных.

## 4. Собранный сайт должен содержать все ресурсы

- Перед коммитом и публикацией проверить, что каждый `<script src>`, CSS, изображение, favicon, manifest, сервис-воркер и другая ссылка ведут на реально существующий ресурс.
- Если сайт или импортёр поставляется архивом / workflow / сборкой, проверить **полноту** содержимого: никакого HTML, который ссылается на отсутствующие `app.js`, `styles.css`, icons, manifest, worker, modules.
- Проверить JavaScript/JSON синтаксис, загрузку всех зависимостей, отсутствие блокирующих консольных ошибок. Импорт-скрипт и workflow должны быть полными, не обрезанными или частично обновлёнными.

## 5. Мобильный браузер и интерактивность

- HTML-документ, открытый в iOS file preview, **не эквивалентен сайту**: там JavaScript может не работать. Для интерактивных страниц нужен реальный HTTPS-URL в Safari.
- Проверить мобильную вёрстку (в частности 360, 390, 414px), 768–1024px, 1280px и широкий desktop. Недопустимы перекрытия header/hero, горизонтальный overflow, обрезанные кнопки/элементы корзины, крошечный текст, потерянные CTA.
- Кликабельность и реальные сценарии: смена тем, навигация, фильтры, поиск, галереи, кнопки, варианты товара, ручной ввод количества, синхронный пересчёт корзины, переходы назад. Тестировать не только наличие элементов, но и результаты нажатия.
- Стили выдерживать в согласованной системе токенов, без накопления конфликтующих каскадов CSS. Не допускать невидимого текста и непредсказуемых fallback-шрифтов.

## 6. GitHub Pages и достоверность публикации

- Для обычных статических сайтов по умолчанию GitHub Pages, если этот способ уже используется проектом; **не переводить самовольно на Vercel/другой сервис**.
- Проверить именно Settings → Pages → source = Deploy from a branch → `main` / `(root)` (либо явную действующую конфигурацию); название ветки в репозитории само по себе не подтверждает Pages-source.
- Проверить, что build/deploy **завершён успешно**, затем открыть **настоящий опубликованный HTTPS-URL** и проверить там JS, CSS, изображения, клики и навигацию. Успешный commit и зелёный workflow не доказывают, что мобильный сайт исправлен.
- На iPhone после обновлений учитывать кэш браузера; использовать cache-busting при проверке новой версии, не выдавать старую страницу за новую.
- Если актуальна доступность из России, учитывать реальную доступность без VPN; не переносить на хостинг без подтверждения.

## 7. Финальный контроль перед выдачей

**Проверка проводится после каждой содержательной доработки**, а не только в конце:
1. Правильный репозиторий/ветка/файл; ничего действующего не перезаписано ошибочно.
2. Все файлы на месте; HTML/CSS/JS/JSON синтаксически и семантически валидны.
3. Все изображения реально отображаются, относятся к правильным товарам и не обрезают главный вид.
4. Нет emoji-иконок, нежелательного системного синего цвета, неверной типографики, неконтролируемого горизонтального скролла.
5. Ключевые интерактивные сценарии проходят на опубликованном сайте, включая узкие экраны.
6. Если сайт не тестировался на реальном устройстве, честно говорить **«не проверено на iPhone»**, а не «исправлено окончательно».
7. После двух повторений одной ошибки — остановить мелкие заплатки, составить полную спецификацию по переписке и пересобрать решение с программной сверкой критериев готовности.

Цель протокола: не допускать переноса одних и тех же ошибок из проекта в проект.
